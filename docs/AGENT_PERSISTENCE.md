# Bounded agents, persistence and approval

Step Functions Standard owns the cloud lifecycle. LangGraph runs a small bounded graph inside the agent job: detection -> conditional hypothesis tests -> candidate planning. Normal observations skip hypothesis testing. Missing or anomalous observations take the test path. Tool arguments pass Pydantic validation and cannot execute generated code.

There is no assumed DynamoDB checkpointer package. This implementation explicitly serializes the bounded `AgentState` into immutable JSON snapshots in S3 at completed-node and negotiation-round boundaries. The run's DynamoDB `AGENTSTATE` record stores the current snapshot key, completed nodes, configuration hash, next node, provider mode and call counts. Full tool evidence stays in the snapshot so arrays do not grow inside DynamoDB records. Each boundary persists the checkpoint before publishing idempotent tool/node events. A restarted graph loads the referenced snapshot, re-enters at detection and skips completed nodes. Completion attempts are persisted before provider invocation; completed negotiation responses are cached by round. A retry reuses a saved response or uses fallback for an interrupted attempt rather than repeating that provider call. Checkpoint failures stop the job for workflow retry instead of being mistaken for provider failures.

Local development persists the same record contract in SQLite and the same snapshots in local JSON files. Tests inject a failure at the start of planning, reopen the saved state, and verify completed investigation is not repeated. Production durability additionally requires the documented live AWS retry check; a local test is not proof of a successful DynamoDB operation.

Each state carries the complete scenario/model configuration hash, agent version and next node. Mismatched persisted inputs are rejected. Local startup resumes unfinished jobs from the same storage directory. Cloud run creation persists metadata/idempotency atomically and starts a uniquely named workflow; a retry can finish dispatch after an interruption between persistence and Step Functions start.

Groq access is checked against the account's model list. The configured model is supplied through the environment; no model ID is hardcoded into browser code. A forced typed fault-test call selects a zone/hypothesis/magnitude based on observed residuals. Additional deterministic tests compare alternate loss, demand and reading-error explanations. Actual completion attempts are bounded to three per run: at most one investigation call (600 maximum completion tokens), and two negotiation-round calls (1,200 maximum completion tokens each). Provider timeout is 12 seconds with no SDK retries. Model-list requests are metadata checks, not LLM completion calls. Per-call model identity, usage, structured proposals, errors, aggregate successful-response token usage and latest quota headers are saved. Missing usage after an interrupted/failed response is not estimated.

Isolation search evaluates single connection closures and complete neighborhood restrictions; schedule search tests explicit available upstream supply; recovery candidates respect repair duration/crew limits. Six logical zone roles are batched into one Groq completion per negotiation round, rather than six independently running model processes. Each proposes its own bounded request, offer and public tradeoff reason. Round two receives actual coordinator trades and remaining water budgets. Typed validation rejects duplicate/missing zones, nonfinite numbers and over-budget proposals. The deterministic coordinator enforces finite donor surplus, connection direction, loss and cumulative capacity before candidate actions reach the engine. Provider failure, malformed proposals, unavailable quota or no agreement produce labelled fallback; mixed rounds are labelled separately. A run without reserve deficits can skip negotiation entirely. The actual-scenario verifier evaluates alternatives and reselects a feasible alternative if a nominal-loss proposal fails. Infeasibility creates an escalation record and cannot be approved.

Approval uses a Step Functions callback task. The preparation Lambda persists the task token server-side and returns immediately; workflow resources, rather than a running invocation, wait for the human. HTTP responses and evidence downloads never include the token. The approval request includes exact plan/scenario versions and an idempotency key. A conditionally created decision record prevents competing approve/reject decisions. Approved actions are simulated only when an approved decision exists, and an existing result key makes job retries return without applying again.

Reports show tool calls, structured arguments, fit summaries, candidate constraint failures, measured balances, outcomes and mode labels. They do not contain private chain-of-thought. Full time series, reports and agent state snapshots live in S3; compact run summaries and checkpoint references live in DynamoDB. Event sequence updates are transactional with event insertion, and duplicate step event keys return the existing event. The publisher follows event persistence so HTTP recovery remains possible after a WebSocket failure.
